結論：真正必要的是 6 張

業務就一件事：進站 → 設 Default Hold → 等全部掃完 + settle → 解 Hold → 結案，加上失敗告警、重試 3 次、整廠停用新 Hold。

現況 12 張是照完整規格攤開的，不是現場最小集。下面 6 張砍不掉；其餘該刪或併。

#表為什麼必要現況從哪裡來
1 hold_order → Oracle MV_NXT_DEF_HOLD_ORDER_BT 一張單的狀態機（WAIT_AI／RELEASE_SENT／CLOSED）＋目前這一筆 Default Hold（Code、Memo、確認／解除時間）。沒有這張就沒有系統。 hold_order ＋ 目前那筆 hold_binding
2 order_wafer 解 Hold 只看「片有沒有 ScanCompletedTime」。Max(掃完時間)+settle 分鐘必須按片存。塞進 JSON 以後沒辦法用 SQL 查。 原表保留，欄位可再瘦（不必管 missing_alarm_type）
3 mes_action 送 MES 前先落庫：凍結 payload、idempotency、第幾次 attempt、回執。沒有這張，Timeout 無法「先查再重送、最多 3 次」。 action_command ＋ action_history 併成一張（一 attempt 一列）
4 incident → Oracle MV_NXT_DEF_HOLD_INCIDENT_BT HOLD_FAILED／HOLD_OVERDUE 等。你那句 WHERE lot_id=… AND status='OPEN' 查這張。寄信狀態可放同一列（現場一告警一封信）。 incident ＋ alarm_outbox
5 MV_NXT_PARAM_BT（既有，不新建） 整廠開關／恢復／心跳。正式環境不建 agent_control，改寫現場這張 PARAM key-value。 SQLite 彩排仍用 agent_control 模擬同一組 key
6 inbound_event 進站事件去重。同一 source_event_id 重送不能再建一張單、也不能把 roster 變更告警開兩次。 原表保留，欄位可瘦

schema_migration 若 DBA 用自己的上版工具，可以不建。查案 View 全部可選，不進生產契約。

MV_NXT_PARAM_BT：正式環境的整廠開關（不新建 agent_control）

現場已有 PARAM 表做 key-value 控制。Oracle adapter 的 SystemControlDao 讀寫這張表，不要 CREATE agent_control。欄位對法之後依現場 DDL 另實作。SQLite 彩排仍用 agent_control 一列，語意相同。

PARAM key 一律 DEFAULT_HOLD_*（不是 VAI_HOLD.*）。實際欄名（例如 PARAM_NAME／PARAM_VALUE）以現場 DDL 為準。

PARAM key值對應 SQLite agent_control 欄誰寫
DEFAULT_HOLD_MODEENABLED／DISABLED_NEW_HOLD／RECOVERY_PENDINGmodeWatchdog 停用；Resume 恢復
DEFAULT_HOLD_DISABLE_REASON例如 overdue_lots=3disable_reasonWatchdog
DEFAULT_HOLD_DISABLE_TRIGGERWATCHDOGdisable_triggerWatchdog
DEFAULT_HOLD_DISABLED_ATUTC ISO 時間disabled_atWatchdog
DEFAULT_HOLD_SPONSOR_ID批准人sponsor_idResume
DEFAULT_HOLD_SPONSOR_APPROVED_ATUTC ISO 時間sponsor_approved_atResume
DEFAULT_HOLD_RESUME_EVIDENCE恢復證據（Resume 參數）Resume
DEFAULT_HOLD_CONTROL_VERSION整數，樂觀鎖control_version每次改 MODE 加一
DEFAULT_HOLD_LAST_HEARTBEAT_ATUTC ISO 時間last_heartbeat_at每輪 Cron（可選）

這不是 YAML：Watchdog 會把 DEFAULT_HOLD_MODE 寫成停用，重啟必須讀 PARAM 而不是設定檔預設 ENABLED。心跳若廠內已有 process Alarm，可以不寫 DEFAULT_HOLD_LAST_HEARTBEAT_AT，以免每分鐘打共享 PARAM 表。

6 張都必要嗎？還能再少嗎？

真正砍不掉的狀態只有三塊：訂單、incident、整廠開關。開關在正式環境不新建表，用 MV_NXT_PARAM_BT。

表能不能拿掉拿掉之後怎麼活你會失去什麼
hold_order 不能 — 沒有訂單就沒有這套系統
incident 不能 — 告警可以沒有訂單（進站資料不齊、心跳死掉）。塞進 hold_order 會漏掉這些。你那句 SQL 也是查這張
整廠開關 不能不記；正式不新建表 Oracle 用既有 MV_NXT_PARAM_BT（key-value）。SQLite 才用 agent_control 彩排 重啟後忘了「已停用」，會繼續對新 Lot 設 Hold
order_wafer 能併 片清單＋ScanCompletedTime 做成 hold_order 上一欄 CLOB／JSON，解 Hold 仍在程式裡算 Max+settle 不能再 SELECT wafer_id FROM order_wafer WHERE lot=…。查案要拆 JSON
mes_action 能併 目前這筆命令＋最多 3 次 attempt 很小，可做成 hold_order 上的 payload + attempt CLOB 不能用 SQL 列出「這張單送了幾次 MES」。retry 邏輯仍在程式裡
inbound_event 最能砍 訂單鍵 (lot, 站, rework) 已經 UNIQUE，重送同一 Lot 不會再建單。若進站是輪詢現況不是「同一事件重送」，這張可以不要 若上游會用同一個 event_id 重送、或同一 Lot 連發兩筆（換 roster），可能重複開 MANUAL_REVIEW

建議檔次：

  • 6 張（現在）：查案全部用 SQL，DBA 也好對。這是「獨立表」的下限，不是「資料」的下限。
  • 4 張：砍 inbound_event＋把 mes_action 併進 hold_order。還留 order_wafer，因為解 Hold 與查片是日常。
  • 正式 Oracle：新建 MV_NXT_DEF_HOLD_ORDER_BT＋MV_NXT_DEF_HOLD_INCIDENT_BT；開關重用 MV_NXT_PARAM_BT。

不建議為了少兩張表，把片清單塞 JSON——解 Hold 的唯一條件就是「每片 ScanCompletedTime」。獨立 order_wafer 對現場查案最有用。若還要再砍，優先砍 inbound_event（看進站介面是不是事件重送）。

12 → 6：每張怎麼處理

現況表建議理由
hold_order留核心
order_wafer留掃完時間按片
hold_binding併進 hold_order本 Agent 只認一筆 Default Hold。ENHL 失敗改 OTHL 是「目前 Code」更新；舊碼留在 mes_action 即可。不再為 SMM Hold 建第二種 binding。
action_command併成 mes_action一張單同時最多一個 in-flight 寫 MES，摘要不必另表
action_history併成 mes_action本來就是「每次 attempt 一列」；兩張是同一件事拆開
incident留告警主檔
alarm_outbox併進 incident現在一開告警就排一封信，1:1。加 mail_status／mail_next_retry_at 就夠
system_control／agent_controlOracle 不建正式用既有 MV_NXT_PARAM_BT；SQLite 才留 agent_control 彩排
discovery_cursor刪／併實際只用來記 heartbeat，不是進站游標。心跳放 agent_control.last_heartbeat_at
observation_snapshot刪應用程式從來沒寫入。決策證據在 log 的 eval.cycle，不是這張表
inbound_event留進站去重
schema_migration可選給 adapter 自己用；DBA 有上版流程就可不要

DDL 與 SQLite 彩排已收到這 6 張（Design/schema/sqlite.sql、oracle.sql）。Memory 單測仍用記憶體物件，不建多餘的表。

你那句 SQL 對哪一張表

SELECT * FROM MV_NXT_DEF_HOLD_INCIDENT_BT
 WHERE lot_id = 'LOT1'
   AND status = 'OPEN';

SQLite 彩排表名是 incident。這是告警主檔：某 Lot 還開著的異常（HOLD_FAILED、HOLD_OVERDUE、AI_RESULT_INVALID…）。status 只准 OPEN／ACKED／RESOLVED。

現有索引是 (status, last_seen_at)，適合「全部未結案」。常按 Lot 查用 (lot_id, status)。

現況 12 張（程式還在用，不是建議再建）

還有哪些要一起考慮（不是表，但接 Oracle 會一起爆）

  1. 雙 DDL 必須同步。加欄改 sqlite.sql 和 oracle.sql。禁止 Python ALTER。測試 test_schema_dual_ddl.py 會擋。
  2. 主鍵 UUID 由應用層產生，不要用 Oracle SEQUENCE 當跨 adapter 契約。
  3. 先 commit Intent，再呼叫 MES。MES 與 DB 不是同一筆分散式交易。網路期間不准長時間 row lock。
  4. Incident 與 Outbox 同交易。commit 成功才寄信；SENT 就結束通知。
  5. 多 Worker 搶單：try_claim 語意必須與 SQLite 契約測試相同（兩個 UoW 同時 claim，只能一個成功）。
  6. 凍結 payload + idempotency_key。retry 同一包；換 Hold Code 是新動作。
  7. 沒 FETCH 到的 MES 欄位不准編造（Created、FirstWaferId、request status）。Watchdog 時間標 ESTIMATED。
  8. UNKNOWN ≠ 空。Hold 查詢不明，不准當成沒有 Hold。
  9. 這套表 ≠ MES。Hold／Release 真實效果在 HoldPort。Oracle 只記我們的訂單與意圖。
  10. PROD 還缺真實 MES／AI／進站 Port。現在 PROD 連 FakeWorld 都會被拒；接 Oracle 同時要接真實 HoldPort／AiPort／SmmPort／Notifier，否則只能把訂單寫進 Oracle、現場仍是假的。
  11. 情境庫 SQLite 不要進生產。scenario_catalog、scenario_orders 是題庫與查案產物。
  12. 連線：ALTER SESSION SET TIME_ZONE = 'UTC'；字元集 AL32UTF8；權限（建表／索引／選寫這 12 張）；連線池；憑證不進 git。
  13. 契約測試。Memory + SQLite 已跑。Oracle 有 DSN 再跑同一檔：重複建單、row_version 衝突、雙 claim、Intent+Incident+Outbox rollback、system_control 重啟仍 DISABLED。
  14. 你的查詢建議索引。常按 Lot 看未結案 → 考慮 CREATE INDEX idx_incident_lot ON incident (lot_id, status); 兩份 DDL 一起加。
  15. DDL 還留 TRANSFER_HOLD。程式已不送 transferHold。CHECK 裡還有這個 enum，接 Oracle 前可決定要不要從兩份 DDL 拿掉（拿掉要重建／遷移）。

建議落地順序

  1. DBA 用 Design/schema/oracle.sql 在空 schema 建 12 張表（可再加 4 個 View）。
  2. 實作 OracleUowFactory + 10 DAO（從 SQLite uow 對譯佔位符／CLOB／時間）。
  3. 把現有 persistence contract 測試接到有 DSN 的 Oracle（沒 DSN 就 skip）。
  4. yaml persistence.backend: oracle；DEV 繼續 sqlite。
  5. 真實 MES／AI／進站 adapter 另案，不要跟表混在一起。
